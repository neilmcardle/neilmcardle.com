<Section title="What is a design token?">

A design token is a single decision that can live everywhere: Figma, CSS, Tailwind config, component props, iOS code. Colors, type sizes, spacing, shadows. Not arbitrary pixel values. Decisions with names.

In Figma, a token is a Variable. In code, it's a CSS custom property (or a Tailwind value, or a map in your component library). Same name, same value, one source of truth.

The power is movement. Change a token in Figma and it flows downstream to every platform that reads it. Change it in code and it syncs back upstream. One graph, not isolated spreadsheets.

Most teams call this a "design-system infrastructure problem." It is, but it's also the differentiator. A system where designers and engineers both trust the source — that means shipping is faster, coherence is automatic, and decisions don't drift.

</Section>

<Section title="Figma Variables as the source">

Figma Variables are the cleanest way to own tokens inside a design tool. You define a color token once (`primary-500`), assign it to components, then export the entire set to your code as JSON or CSS custom properties.

Set up Variables in Figma:
- Create a library file. One per design system.
- Scope variables by type: `color`, `typography`, `spacing`, `shadow`, `radius`.
- Use naming that works across platforms: `primary-500`, `spacing-4`, `font-body`.
- Create mode overrides for dark mode and other themes.
- Export or read via API.

When you reference a variable in a component's fill, stroke, text size — Figma now knows the intent. "This button uses `primary-500`" becomes a traceable link, not a detached screenshot. A designer can hand a developer the file and say "extract every variable" and the developer has a complete map.

The sync lives either in code (import the JSON, read the API) or via a platform like Tokens Studio. Both work. The key is: Figma is the source, not a side effect.

</Section>

<Section title="CSS custom properties and naming">

CSS custom properties (variables) are the universal bridge. Every platform reads CSS or can be converted to it.

Define your tokens as custom properties at the root of your CSS:

```css
:root {
  --color-primary-500: #2563eb;
  --color-primary-600: #1d4ed8;
  --color-text: #1f2937;
  --spacing-4: 1rem;
  --spacing-8: 2rem;
  --radius-md: 0.5rem;
  --shadow-md: 0 4px 12px rgba(0, 0, 0, 0.1);
  --font-body: -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif;
  --font-size-body: 1rem;
  --line-height-body: 1.5;
}
```

Naming convention matters. Prefix by type (`--color-`, `--spacing-`), then semantic role if it exists (`primary-500`), then fallback to numeric scale (`200`, `400`, `600`).

Use them in your CSS:

```css
.button {
  background: var(--color-primary-500);
  padding: var(--spacing-4) var(--spacing-8);
  border-radius: var(--radius-md);
  font-family: var(--font-body);
  font-size: var(--font-size-body);
  line-height: var(--line-height-body);
}

.button:hover {
  background: var(--color-primary-600);
}
```

Custom properties are dynamic. They cascade. They can be redefined in a media query or a class. They're the simplest possible bridge between Figma and the browser.

</Section>

<Section title="Tailwind theme integration">

Tailwind is built for tokens. Your `tailwind.config.js` theme object is exactly where design tokens become utility classes.

Extract your Figma variables (or CSS custom properties) and map them into the Tailwind config:

```javascript
// tailwind.config.js
export default {
  theme: {
    extend: {
      colors: {
        primary: {
          500: "#2563eb",
          600: "#1d4ed8",
        },
        secondary: {
          500: "#7c3aed",
          600: "#6d28d9",
        },
      },
      spacing: {
        4: "1rem",
        8: "2rem",
        12: "3rem",
      },
      borderRadius: {
        md: "0.5rem",
        lg: "0.75rem",
      },
      fontSize: {
        body: ["1rem", { lineHeight: "1.5" }],
        heading: ["1.5rem", { lineHeight: "1.25" }],
      },
    },
  },
};
```

Now every token becomes a Tailwind class. `bg-primary-500`, `p-4`, `rounded-md`, `text-body`. The HTML is clean, the tokens are centralized, and a designer can read the Tailwind config as a contract.

When you need to change a color, you edit the config once and it applies everywhere. Figma variables sync to the config (either manually or via a build step), and the site updates on deploy.

Tailwind doesn't need CSS custom properties underneath. But if you want to support runtime theme switching (dark mode, user preferences), custom properties at the root let you override values without rebuilding CSS.

</Section>

<Section title="Themed dark mode via tokens">

Dark mode done right doesn't live in utility overrides (`dark:bg-gray-900`). It lives in tokens.

Define a dark mode set of variables in Figma. Same token names, different values. Export both light and dark to a configuration object:

```javascript
// tokens.js
export const lightTheme = {
  "color-bg": "#ffffff",
  "color-text": "#1f2937",
  "color-primary-500": "#2563eb",
  "color-border": "#e5e7eb",
};

export const darkTheme = {
  "color-bg": "#111827",
  "color-text": "#f3f4f6",
  "color-primary-500": "#3b82f6",
  "color-border": "#374151",
};
```

Apply them as CSS custom properties on the root element:

```javascript
// theme.js
function setTheme(isDark) {
  const tokens = isDark ? darkTheme : lightTheme;
  const root = document.documentElement;
  
  Object.entries(tokens).forEach(([key, value]) => {
    root.style.setProperty(`--${key}`, value);
  });
  
  localStorage.setItem("theme", isDark ? "dark" : "light");
}

// On page load
const isDark = localStorage.getItem("theme") === "dark";
setTheme(isDark);
```

Write your components in terms of tokens:

```css
.button {
  background: var(--color-primary-500);
  color: var(--color-text);
  border: 1px solid var(--color-border);
}
```

Switch themes and all colors update. No cascade of `dark:` utilities. No theme-specific component variants. One component, two token sets.

</Section>

<Section title="Component API: props and variants">

A component's API should be minimal and intentional. Props for things users actually control. No prop for every possible style.

```typescript
// Button.tsx
interface ButtonProps {
  children: React.ReactNode;
  variant?: "primary" | "secondary" | "ghost";
  size?: "sm" | "md" | "lg";
  disabled?: boolean;
  onClick?: () => void;
}

export function Button({
  children,
  variant = "primary",
  size = "md",
  disabled = false,
  onClick,
}: ButtonProps) {
  // Implementation uses variants, not arbitrary props
  return (
    <button
      onClick={onClick}
      disabled={disabled}
      data-variant={variant}
      data-size={size}
    >
      {children}
    </button>
  );
}
```

Notice what's *not* a prop: `color`, `padding`, `fontSize`, `borderRadius`. Those flow from `variant` and `size`. A component should expose intent, not pixels.

Variant is a single, deliberately chosen value. Not a free string. The component owner controls what combinations exist and makes sure they match the design system.

</Section>

<Section title="Variants: CVA and alternatives">

Class Variance Authority (CVA) makes variant logic explicit and type-safe:

```typescript
// button.ts
import { cva, type VariantProps } from "class-variance-authority";

const buttonStyles = cva("px-4 py-2 rounded-md font-semibold transition-colors", {
  variants: {
    variant: {
      primary: "bg-primary-500 text-white hover:bg-primary-600",
      secondary: "bg-secondary-500 text-white hover:bg-secondary-600",
      ghost: "bg-transparent text-primary-500 hover:bg-primary-50",
    },
    size: {
      sm: "text-sm px-2 py-1",
      md: "text-base px-4 py-2",
      lg: "text-lg px-6 py-3",
    },
  },
  defaultVariants: {
    variant: "primary",
    size: "md",
  },
});

type ButtonVariants = VariantProps<typeof buttonStyles>;

export function Button({ variant, size, children }: ButtonVariants & { children: React.ReactNode }) {
  return <button className={buttonStyles({ variant, size })}>{children}</button>;
}
```

CVA generates the class string based on variant values, automatically type-checks combinations, and keeps the intent readable.

If you prefer vanilla CSS or a framework without CVA, use data attributes and CSS selectors:

```css
/* Vanilla approach */
[data-variant="primary"][data-size="md"] {
  padding: var(--spacing-4) var(--spacing-8);
  background: var(--color-primary-500);
  font-size: var(--font-size-body);
}
```

Both work. CVA is faster for large systems. Vanilla CSS is more portable. Pick one and be consistent.

</Section>

<Section title="Documenting components">

A design system lives or dies on documentation. A component without a doc is a secret.

Use Storybook or a custom component browser. Write a story for each variant combination:

```typescript
// Button.stories.ts
import type { Meta, StoryObj } from "@storybook/react";
import { Button } from "./Button";

const meta: Meta<typeof Button> = {
  component: Button,
  tags: ["autodocs"],
  argTypes: {
    variant: {
      control: { type: "select" },
      options: ["primary", "secondary", "ghost"],
    },
    size: {
      control: { type: "select" },
      options: ["sm", "md", "lg"],
    },
    disabled: { control: "boolean" },
  },
};

export default meta;
type Story = StoryObj<typeof meta>;

export const Primary: Story = {
  args: {
    variant: "primary",
    size: "md",
    children: "Click me",
  },
};

export const Secondary: Story = {
  args: {
    variant: "secondary",
    children: "Secondary action",
  },
};

export const Disabled: Story = {
  args: {
    variant: "primary",
    disabled: true,
    children: "Disabled",
  },
};
```

Include prose: when to use each variant, how props interact, what states exist, accessibility notes. A screenshot is proof. A story with documentation is a contract.

Publish your Storybook. Designers and developers both reference it. It becomes the source of truth for what the component does, and the playground where you test it.

</Section>

<Section title="Syncing tokens bidirectionally">

The real magic: tokens flow both directions. A designer changes a color in Figma, and it appears in the code. An engineer tweaks a spacing value, and it updates in Figma.

Use Tokens Studio for Figma (a plugin) or write a sync script.

Tokens Studio approach:
- Define tokens in a JSON file in your repo.
- Install the Tokens Studio plugin in Figma.
- Link the JSON as the remote source.
- Changes in Figma sync to the JSON. Changes in the JSON sync to Figma.
- Update your CSS and Tailwind config from the same JSON.

Script approach:

```bash
# export-tokens.js
const figmaTokens = await fetchFromFigmaAPI();
const cssOutput = generateCSSCustomProperties(figmaTokens);
const tailwindOutput = generateTailwindConfig(figmaTokens);

fs.writeFileSync("src/tokens.css", cssOutput);
fs.writeFileSync("tailwind.config.js", tailwindOutput);
```

Run the script on CI or on-demand. Keep the source file (Figma or JSON) as the single origin, and everything else derives from it.

When a change lands in the source, it propagates. No manual copy-paste. No drift. No "why does the Figma file say one thing and the code say another?"

</Section>

<Section title="One source of truth">

This is the checkpoint. After building a design-token system, ask:

1. Is there one place where color decisions live? One place where spacing decisions live? Not scattered across Figma, a Notion doc, and three config files.
2. Can a designer make a change in Figma and see it in the running app without asking an engineer to rebuild?
3. Can an engineer tweak a value for accessibility or performance and have it sync back to Figma?
4. Do components have an API that a new team member can understand in five minutes?
5. Does the codebase have one way to define variants, not three?

If the answer to all five is yes, you have a design system. It scales because it's coherent. A new component takes minutes to add because the patterns are clear. Designers and engineers speak the same language because the tokens are the language.

This is craft. Systems this transparent, this well-documented, cost more upfront but multiply on every subsequent decision. They're also the differentiator between teams that ship confidence and teams that ship surprises.

</Section>
