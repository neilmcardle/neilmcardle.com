# M7 — TypeScript for UI

## The promise

You've written a data-backed card in M6: a component that fetches real data, renders it, and handles loading and error states. Right now it has no guard rails. If the API changes shape, you won't know until the page breaks at runtime. If you rename a prop and forget to update the call site, React will silently render nothing.

**TypeScript catches all of that before you hit save.**

This module adds type safety to M6's card. You'll define types for the API response, the component props, and the state. You'll run the same fetch logic but with TypeScript watching your back. By the end, you'll write a `fetch` that proves the data shape the moment the response lands — and a component that screams if you pass it the wrong props.

**Through-thread:** Language vs. framework. TypeScript is a language layer; React is a framework layer. Learn to separate them.

---

## What types add

You already write JavaScript. TypeScript is JavaScript plus one thing: **before your code runs, someone checks that the data has the shape you expect.**

Consider this. In M6, you might have written:

```js
const Card = ({ name, description, image }) => (
  <div>
    <h2>{name}</h2>
    <p>{description}</p>
    <img src={image} alt={name} />
  </div>
)
```

If a parent passes `name: undefined` or omits `image` entirely, the code runs. React renders. The browser shows a broken card. You discover the bug when you see it.

Now, in TypeScript:

```tsx
type CardProps = {
  name: string
  description: string
  image: string
}

const Card = ({ name, description, image }: CardProps) => (
  <div>
    <h2>{name}</h2>
    <p>{description}</p>
    <img src={image} alt={name} />
  </div>
)
```

If someone tries to call `<Card name={undefined} />`, TypeScript *stops the file from compiling*. The error is right there, in your editor, before you run anything. You fix the call site and move on.

**Types are your tests before tests.** They catch entire categories of bugs at edit time, not runtime.

### The cost

TypeScript adds syntax. `type`, `:`, `{}`. The file gets longer. Some people find it noise.

**The trade:** a 20% longer file that screams when you mess up, vs. a 20% shorter file that silently breaks in production. In a team, or on a growing codebase, TypeScript pays for itself the first time you rename a field.

## Structural typing — TypeScript's philosophy

Other languages check types by name. `class Dog` is different from `class Animal`, even if they have identical fields. TypeScript doesn't.

```ts
type Person = {
  name: string
  age: number
}

type Employee = {
  name: string
  age: number
}

const person: Person = { name: "Alice", age: 30 }
const employee: Employee = person  // OK. TypeScript sees the same shape.
```

TypeScript looks at *shape*, not *name*. If it has `name` and `age` as strings/numbers, it's a `Person` *and* an `Employee`.

This is called **structural typing**. The structure is what matters. It's why TypeScript feels more flexible than other typed languages — you can pass any object that *looks like* the type, regardless of where it came from.

It also means types are a *conversation*, not a command. You're not declaring "this is a Dog"; you're saying "this thing quacks and has feathers, so I'll treat it as a Duck."

## Typing API responses — knowing what data looks like

M6 fetched data from an API. The response was JSON:

```json
{
  "id": 1,
  "title": "Learning TypeScript",
  "author": "Neil",
  "rating": 4.8,
  "price": 29.99
}
```

In plain JavaScript, you'd write:

```js
const response = await fetch("https://api.example.com/book/1")
const book = await response.json()  // What is book? No one knows.
console.log(book.title)             // Works if the API returns title. Breaks if it doesn't.
```

`book` is a mystery. You're guessing it has `title`. If the API changes, your guess is wrong.

In TypeScript:

```ts
type Book = {
  id: number
  title: string
  author: string
  rating: number
  price: number
}

const response = await fetch("https://api.example.com/book/1")
const book: Book = await response.json()
console.log(book.title)  // TypeScript knows this exists
console.log(book.unknown) // TypeScript ERROR: Book has no unknown field
```

Now `book` is typed. TypeScript **knows** the shape. If you try to read `book.unknown`, the editor shows red before you run anything.

### The pattern: define, then narrow

Here's the rhythm:

1. **Look at the API response.** What fields does it have? What types are they?
2. **Write a type that matches.** This is structural typing — you're not naming the API response, you're describing its shape.
3. **Type the variable** where you parse the response: `const book: Book = await response.json()`
4. **Use it.** TypeScript now watches every field access.

### API response is runtime data — types can't check it

There's a catch. **The type you write is a promise, not a guarantee.**

```ts
type Book = {
  id: number
  title: string
}

const book: Book = await response.json()
```

TypeScript *assumes* the response matches `Book`. If the real API returns `{ id: "not a number", title: null }`, TypeScript won't catch it. The type is checked at *compile time*, not *runtime*. The data came from the internet — it could be anything.

**Solution:** at the boundary between your app and the world, validate the data. Defensive code matters:

```ts
if (typeof book.id !== 'number' || typeof book.title !== 'string') {
  throw new Error('API response has wrong shape')
}
```

Or use a library like `zod` that validates at runtime. For now, be honest: your type says "I *expect* this shape." The validation is your promise that the API will deliver.

## Typing props — what a component accepts

A component is a function. It takes props (an object), returns JSX.

```tsx
const Card = (props) => (
  <div>
    <h2>{props.title}</h2>
  </div>
)
```

In plain JavaScript, `props` is a mystery blob. You don't know what keys it should have.

In TypeScript, you type it:

```tsx
type CardProps = {
  title: string
  description: string
}

const Card = (props: CardProps) => (
  <div>
    <h2>{props.title}</h2>
    <p>{props.description}</p>
  </div>
)
```

Now, whoever calls `<Card />` gets instant feedback if they forget a prop or pass the wrong type:

```tsx
<Card title="Hello" description="World" />  // OK
<Card title="Hello" />                       // ERROR: missing description
<Card title={42} description="World" />     // ERROR: title should be string, not number
```

### Destructuring + typing

Most components destructure their props inline:

```tsx
const Card = ({ title, description }: CardProps) => (
  <div>
    <h2>{title}</h2>
    <p>{description}</p>
  </div>
)
```

This is cleaner. The type still applies. TypeScript knows what `title` and `description` are.

## Type errors are feedback

When TypeScript complains, read the error. It's not a penalty; it's information.

```ts
type Book = { title: string }
const book: Book = { title: 42 }
// ERROR: Type 'number' is not assignable to type 'string'.
```

Translation: "You said `book.title` is a string. You're trying to assign a number. That's a contradiction."

The error tells you *what's wrong* and *where*. Fix it and move on.

If an error feels cryptic, it usually means:
1. Your type is wrong (fix the type)
2. Your data is wrong (fix the data)
3. You've typed something too broadly (narrow the type)

Cryptic errors are rare. Most are direct.

## Guided build: Retype M6's card

Let's take M6's data-backed card and add TypeScript, piece by piece.

### Start: the file structure

You're working with a React component. Create a `.tsx` file (TypeScript + JSX, not `.js`).

```tsx
// Book.tsx
import { useState, useEffect } from 'react'
```

### Step 1: Type the API response

What does your API return? Let's say it's a book:

```json
{
  "id": 1,
  "title": "The Design of Everyday Things",
  "author": "Don Norman",
  "coverUrl": "https://...",
  "rating": 4.7
}
```

Write a type for it:

```tsx
type Book = {
  id: number
  title: string
  author: string
  coverUrl: string
  rating: number
}
```

This says: "A Book is an object with these five fields, each with these types."

### Step 2: Type the fetch

Fetch returns a response. Parse it. Type the result:

```tsx
const fetchBook = async (bookId: number): Promise<Book> => {
  const response = await fetch(`/api/books/${bookId}`)
  if (!response.ok) throw new Error('Failed to fetch')
  const book: Book = await response.json()
  return book
}
```

Read this out loud:
- `fetchBook` is a function
- It takes `bookId` (a number)
- It returns a `Promise<Book>` (eventually, a Book)
- Inside, we parse the response and type it as `Book`
- If anything goes wrong, we throw

TypeScript now guarantees: if `fetchBook` succeeds, you get a real `Book`.

### Step 3: Type the component props

Your component displays a book. What does it need?

```tsx
type BookCardProps = {
  bookId: number
}

const BookCard = ({ bookId }: BookCardProps) => {
  const [book, setBook] = useState<Book | null>(null)
  const [error, setError] = useState<string | null>(null)
  const [loading, setLoading] = useState(false)

  // ...
}
```

Read this:
- The component takes a `bookId` (number)
- `book` state is either a `Book` or `null` (it starts empty)
- `error` state is either a `string` or `null`
- `loading` is a boolean

This is explicit. You're saying exactly what shapes these values can take.

### Step 4: Fetch on mount

```tsx
useEffect(() => {
  const load = async () => {
    try {
      setLoading(true)
      const fetched = await fetchBook(bookId)
      setBook(fetched)  // TypeScript knows fetched is a Book
      setError(null)
    } catch (err) {
      setError(err instanceof Error ? err.message : 'Unknown error')
      setBook(null)
    } finally {
      setLoading(false)
    }
  }

  load()
}, [bookId])
```

Notice: when we call `setBook(fetched)`, TypeScript knows `fetched` is a `Book`. When we set the error, we handle the fact that `err` might not be an Error object. This is defensive + typed.

### Step 5: Render based on state

```tsx
if (loading) return <div>Loading...</div>
if (error) return <div>Error: {error}</div>
if (!book) return <div>No book found</div>

return (
  <div className="card">
    <img src={book.coverUrl} alt={book.title} />
    <h2>{book.title}</h2>
    <p>{book.author}</p>
    <span className="rating">{book.rating}/5</span>
  </div>
)
```

Here's where TypeScript shines. Inside the `return`, TypeScript *knows* `book` is not null. You don't need to guard it again. Access `book.title`, `book.coverUrl` — TypeScript has verified they exist.

### The complete component

```tsx
import { useState, useEffect } from 'react'

type Book = {
  id: number
  title: string
  author: string
  coverUrl: string
  rating: number
}

const fetchBook = async (bookId: number): Promise<Book> => {
  const response = await fetch(`/api/books/${bookId}`)
  if (!response.ok) throw new Error('Failed to fetch')
  const book: Book = await response.json()
  return book
}

type BookCardProps = {
  bookId: number
}

const BookCard = ({ bookId }: BookCardProps) => {
  const [book, setBook] = useState<Book | null>(null)
  const [error, setError] = useState<string | null>(null)
  const [loading, setLoading] = useState(false)

  useEffect(() => {
    const load = async () => {
      try {
        setLoading(true)
        const fetched = await fetchBook(bookId)
        setBook(fetched)
        setError(null)
      } catch (err) {
        setError(err instanceof Error ? err.message : 'Unknown error')
        setBook(null)
      } finally {
        setLoading(false)
      }
    }
    load()
  }, [bookId])

  if (loading) return <div>Loading...</div>
  if (error) return <div>Error: {error}</div>
  if (!book) return <div>No book found</div>

  return (
    <div className="card">
      <img src={book.coverUrl} alt={book.title} />
      <h2>{book.title}</h2>
      <p>{book.author}</p>
      <span className="rating">{book.rating}/5</span>
    </div>
  )
}

export default BookCard
```

Every line is guarded. If you rename `coverUrl` to `image` in the `Book` type but forget to update the JSX, TypeScript stops you. If you try to pass `bookId: "wrong-type"`, TypeScript shows red. This is the confidence you buy.

You have a real API at `https://jsonplaceholder.typicode.com/posts/1`. It returns:

- Calls the API (use the real URL: `https://jsonplaceholder.typicode.com/posts/${postId}`)
- Returns a `Promise<Post>`
- Throws an error if the response is not OK

Paste this in your editor. You should see no red squiggles. If you do, read the error and fix it.

**Part 3: Spot a type error**

Here's a component with a bug:

```tsx
type PostCardProps = {
  title: string
  content: string
}

const PostCard = ({ title, content }: PostCardProps) => (
  <div>
    <h2>{title}</h2>
    <p>{content}</p>
  </div>
)

// Caller
<PostCard title="Hello" summary="World" />
```

What's wrong? TypeScript should tell you. What does the error say?

**Part 4: Fix it**

Either:
- Change the component to accept `summary` instead of `content`, or
- Change the caller to pass `content` instead of `summary`

Run the code. No TypeScript errors.

**Success criterion:** You've defined a type, typed a fetch, and caught a prop mismatch before runtime.

## Common designer mistakes

### 1. Over-typing

```ts
// Too much
const title: string = "Hello"
const count: number = 0
```

TypeScript can *infer* types from the value. `"Hello"` is obviously a string; `0` is obviously a number. You can write:

```ts
// Better
const title = "Hello"
const count = 0
```

TypeScript figures it out. Only type when the type isn't obvious from context — like a `useState` with an initial `null`.

### 2. The mystery `any`

```ts
const book: any = await response.json()
```

`any` means "I give up on type safety here." Don't. It defeats the purpose. If you don't know the type, define it. If you can't define it, you have a design problem.

### 3. Typing the caller, not the contract

```tsx
// Wrong
const Card = (props) => { ... }
<Card data={book} />  // Caller decides type?

// Right
type CardProps = { data: Book }
const Card = ({ data }: CardProps) => { ... }
<Card data={book} />  // Contract is clear
```

The component defines what it expects. The caller conforms to it.

### 4. Forgetting `Promise`

```ts
// Wrong — this doesn't return a string, it returns a promise
const getName = async () => {
  return "Neil"
}

// Right
const getName = async (): Promise<string> => {
  return "Neil"
}
```

`async` functions always return a Promise. Type them explicitly.

## Through-threads

### Language vs. framework (TypeScript → JavaScript)

TypeScript is a *language layer*. React is a *framework layer*. The more you understand the language, the better you use the framework.

You learned JavaScript first (M5). Then you learned React (M8, coming). Now you're learning TypeScript — the typed version of JavaScript. This order matters.

Some frameworks (Vue, Angular) have their own syntax for types. React just uses TypeScript's syntax directly. That's why mastering TypeScript pays dividends everywhere.

**Why it matters:** When you hit a weird React error, you often need to think about the JavaScript underneath. When TypeScript screams, you need to know whether the problem is the language (the type definition) or the framework (how React uses it). Separate the two, and debugging becomes linear.
